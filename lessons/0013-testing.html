Unit test — pola group + setUp (AAA)

Tantangan no. 1 dosen ("5 test untuk class Kalkulator") diadaptasi: class yang diuji bukan Kalkulator matematika, tapi AnemiaLogic — logika yang beneran dipakai app (batas Hb 12.0 dari dashboard M7, sekarang jadi satu sumber kebenaran yang di-refactor ke class ini). Struktur test-nya persis materi dosen:

group('AnemiaLogic.tingkatKeparahan', () {
  test('klasifikasi lengkap lima nilai', () {
    expect(AnemiaLogic.tingkatKeparahan(15.0), TingkatAnemia.normal);
    expect(AnemiaLogic.tingkatKeparahan(11.5), TingkatAnemia.ringan);
    expect(AnemiaLogic.tingkatKeparahan(9.8), TingkatAnemia.sedang);
    expect(AnemiaLogic.tingkatKeparahan(6.9), TingkatAnemia.berat);
  });

  test('EDGE: batas band 11.0 = ringan, 8.0 = sedang, 7.9 = berat', () { ... });
});

Pola AAA: Arrange (siapkan data, bisa di setUp), Act (panggil fungsi), Assert (cek dengan expect).

Matcher yang paling sering kepake

// Dari materi dosen → yang beneran dipake di test kita:
expect(5, 5);                                  // sama persis
expect(persen, closeTo(66.67, 0.01));          // double approx → persentase
expect(AnemiaLogic.statusAnemia(10.2), isTrue);
expect(AnemiaLogic.statusAnemia(12.0), isFalse); // EDGE boundary
expect(() => ..., throwsArgumentError);        // (di materi; kita pakai buat cek lempar)

Poin penting dari best practice dosen: test edge case — list kosong (jangan bagi nol), batas persis 12.0 (ternyata normal, bukan anemia!), 0.0 ekstrem.

Widget test — finder & aksi

Tantangan no. 2: ProfileCard(nama, email) — dipasang beneran di header detail Direktori (data API M10), avatar inisial + nama + email + subtitle opsional:

testWidgets('ProfileCard menampilkan nama & email + inisial avatar', (t) async {
  await t.pumpWidget(const MaterialApp(
    home: Scaffold(body: ProfileCard(nama: 'Silvi Rahmawati', email: 'silvi@example.com')),
  ));
  expect(find.text('Silvi Rahmawati'), findsOneWidget);
  expect(find.text('silvi@example.com'), findsOneWidget);
  expect(find.text('S'), findsOneWidget); // inisial
});

Tantangan no. 3 (bonus dosen: widget test tambah/toggle/hapus): jadwal udah ditest di level model (M9) — sekarang dikomplitin di level UI: centang CheckboxListTile, hapus item, Hapus Semua Selesai. Pelajaran nyata: find.byIcon(Icons.delete_outline) ambigu kalau ada 2 item → harus find.descendant(of: find.widgetWithText(CheckboxListTile, 'Budi Santoso'), ...).

Menguji form — validasi input kosong (dari materi dosen)

// Mirip "Login menolak email kosong" → form tambah pasien (M10)
testWidgets('Tambah pasien: form kosong → SnackBar merah validasi', (t) async {
  await pumpDirektori(t);
  await t.tap(find.byIcon(Icons.person_add));
  await t.pumpAndSettle();
  await t.tap(find.text('Simpan'));   // submit tanpa isi apa-apa
  await t.pump();
  expect(find.text('Nama & email wajib diisi'), findsOneWidget);
});

Bukan cuma jalan senang: branch validasi yang biasanya kelewat sekarang ketutup test.

Mocking HTTP — deviasi tercatat (mockito vs MockClient)

Dosen pakai mockito + build_runner (codegen). Kita sejak M10 pakai MockClient bawaan package:http/testing — hasilnya sama (test cepat, offline, nggak hit server), tapi nggak butuh dependency codegen & generate. Prinsipnya identik: JANGAN hit server beneran di test.

Integration test — app nyata di emulator

Dibikin integration_test/app_test.dart (package SDK integration_test): happy path end-to-end — buka app → catat Silvi ke jadwal → toggle selesai → hapus → kosong. Dua keputusan jujur: (1) nggak kebawa flutter test biasa (default cuma folder test/), jadi suite kita tetap cepat; (2) nggak buka tab Direktori karena butuh jaringan/API. Test-nya idempoten (bersihin sisa "selesai" dari run sebelumnya).

// Jalanin (butuh emulator/device aktif — belum dijalankan sesi ini, RAM):
$ flutter test integration_test/app_test.dart

Coverage — berapa banyak kode yang ketest?

$ flutter test --coverage        # → coverage/lcov.info
$ genhtml coverage/lcov.info -o coverage/html   # butuh tool lcov

Di mesin ini genhtml nggak ada, jadi dihitung manual dari lcov.info: 86.6% baris lib/ ketutup test (568/656, 16 file) — sisa 13.4% mostly branch error & callback UI (kamera, dll) yang emang butuh device nyata / belum di-test.

Best practice (dari dosen, dibuktikan di project kita)

  1. Berikan Key di widget penting — kita pakai ValueKey(foto.path) di galeri, dst.
  2. Pisahkan logic dari UI — AnemiaLogic, service, dan store pisah dari widget; itu kenapa “murni Dart” itu gampang di-unit-test.
  3. Test edge case — batas 12.0, list kosong, input kosong, server 500 (error state Direktori).
  4. Jangan test framework — nggak ada test buat ngebuktiin setState jalan.

Tugas praktik

  1. Jalanin semua test: flutter test --concurrency=1 → 35 lulus.
  2. Coverage: flutter test --coverage --concurrency=1 → cek coverage/lcov.info (86.6% lib/).
  3. Kalau emulator aktif: flutter test integration_test/app_test.dart — integration test beneran jalan di device. (Butuh RAM luang — tutup IDE/browser.)
  4. Coba rusakin sesuatu (misal ubah batas 12.0 → 13.0) → test AnemiaLogic harus ikut gagal. Itu gunanya test: nangkep regresi.
  5. Explore: tab Direktori → detail → header sekarang ProfileCard dengan inisial + email.
Catatan jujur: coverage 86.6% itu baris lib/ yang ketutup test — bukan jaminan "bebas bug", tapi jaring pengaman yang bikin tiap modul berikutnya (build, publish, final project) berani diutak-atik.

Kuis singkat

Q1: Urutan piramida testing dari yang PALING cepat ke paling lambat…

Unit milidetik & terisolasi; widget butuh render; integration jalan di device nyata.

Q2: Tantangan "class Kalkulator" diadaptasi jadi…

Jdi class murni (statusAnemia, tingkatKeparahan, persentase, deltaHb) — makin nyambung ke misi app.

Q3: Mocking HTTP di project kita pakai…

Deviasi tercatat: hasil sama (test offline & cepat), tanpa dependency extra — prinsip dosen tetap dipegang.

Q4: find.byIcon(delete_outline) ambigu pas ada 2 item, solusinya…

Targetkan ikon di dalam konteks baris spesifik biar cuma satu match.

Q5: Kenapa integration test dipisah di folder integration_test?

Integration butuh device & lambat — di-pisah biar suite unit/widget harian nggak kena.
