Data jadwal lo sekarang disimpen beneran 💾

Materi asli dosen: Modul 11: Local Storage (SQLite).

Ini modul yang paling ditunggu: sejak Modul 9, jadwal pemantauan cuma hidup di memori — tutup app, ilang. Sekarang data **persist**: restart app, jadwal lo tetep ada. Bonus dosen (login persist pakai SharedPreferences) kita adaptasi biar masuk konteks app: "kembali ke tab terakhir yang lo buka".

SharedPreferences — key-value persisten

// SIMPAN
final prefs = await SharedPreferences.getInstance();
await prefs.setInt('tab_terakhir', 3);

// BACA (null kalau belum pernah disimpan)
final saved = prefs.getInt('tab_terakhir');

Dipasang di HomeShell: waktu ganti tab → simpan index-nya; waktu app start → pulihkan. Bonus dosen "login persist" diadaptasi ke fitur ini biar masuk konteks app (kita nggak punya login).

SQLite — model + toMap/fromMap

Pola Note dari dosen, untuk item jadwal kita:

class JadwalItem {
  final int? id;            // null sebelum masuk DB → autoincrement
  final String namaPasien;
  bool selesai;
  final String dibuatAt;    // ISO 8601

  Map<String, dynamic> toMap() => {
        'id': id, 'nama': namaPasien,
        'selesai': selesai ? 1 : 0,   // SQLite nggak kenal bool, pakai 0/1
        'dibuatAt': dibuatAt,
      };

  factory JadwalItem.fromMap(Map<String, dynamic> m) => ...;
}

DatabaseHelper singleton (pola dosen)

class JadwalDbStore implements JadwalStore {
  JadwalDbStore._();
  static final JadwalDbStore instance = JadwalDbStore._();
  static Database? _db;

  Future<Database> get _database async {
    if (_db != null) return _db!;
    final path = join(await getDatabasesPath(), 'anemia_jadwal.db');
    _db = await openDatabase(path, version: 1,
      onCreate: (db, _) => db.execute('''
        CREATE TABLE jadwal (
          id INTEGER PRIMARY KEY AUTOINCREMENT,
          nama TEXT NOT NULL,
          selesai INTEGER NOT NULL DEFAULT 0,
          dibuatAt TEXT NOT NULL
        )'''));
    return _db!;
  }

  // CRUD: query/insert/update/delete pakai SQL + whereArgs ($,-injection aman)
}

Kenapa model nggak nyentuh SQLite langsung?

abstract class JadwalStore {
  Future<List<JadwalItem>> muatSemua();
  Future<int> tambah(JadwalItem item);
  Future<void> update(JadwalItem item);
  Future<void> hapus(int id);
}

Soalnya sqflite butuh plugin native yang nggak ada di widget test. JadwalModel cuma kenal interface ini — di produksi diisi JadwalDbStore.instance, di test diisi InMemoryJadwalStore (fake di test/fakes/). Bonusnya: logika bisnis berdiri sendiri dari database, dan test "persisten" bisa membuktikan data balik lagi setelah "restart" tanpa perlu SQLite beneran.

class JadwalModel extends ChangeNotifier {

Semua operasi sekarang async dan pakai id (bukan index) — karena data bisa beda urutan setelah reload dari DB.

Tugas praktik (10 menit)

  1. flutter run → Beranda → Silvi → Catat ke Jadwal → tab Jadwal → centang → telpon tombol q buat keluar app.
  2. Buka app lagi → tab Jadwal → data masih ada (persist SQLite!). Ini bedanya dari Modul 9.
  3. Pindah ke tab Direktori → keluar app → buka lagi → app balik ke tab Direktori (SharedPreferences).
  4. Di tab Jadwal: hapus satu item (ikon 🗑), centang beberapa, cobain Hapus Semua Selesai.
  5. Tantangan dosen (opsional): kolom kategori di tabel + filter per kategori — sekarang lo punya toolset CRUD lengkap buat ngerjainnya.
Catatan jujur: isi tabel jadwal lo beneran nyimpen di database SQLite perangkat (anemia_jadwal.db). Di final project, data pasien + hasil lab juga bakal dilewatin jalur yang sama (atau API asli — pilihan M16).

Kuis singkat

Q1: Data kecil key-value (setting, flag) pakai…

SharedPreferences = Map persisten buat data primitif kecil; SQLite buat data terstruktur/relasional.

Q2: SQLite nggak punya tipe bool, jadi selesai disimpan sebagai…

selesai ? 1 : 0 di toMap, dibaca balik dengan m['selesai'] == 1.

Q3: Kenapa JadwalModel pake interface JadwalStore, bukan langsung sqflite?

Test inject fake store in-memory; produksi pakai JadwalDbStore. Logika bisnis jadi bisa diuji offline (dependency injection).

Q4: Ilangnya data setelah app ditutup? Solusinya…

State di memori (ChangeNotifier) ilang pas proses mati — makanya persist ke disk.

Q5: Operasi JadwalModel pindah dari index ke…

Setelah load ulang dari DB, urutan bisa beda — id (primary key) yang aman untuk update/hapus.
